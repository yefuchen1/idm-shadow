## 已验证的链路

用本地测试服务器（`cargo run -p idm-shadow-engine --example test_server`）跑通：

- **扩展 / 油猴 → bridge → 引擎**：`POST /api/v1/tasks` 投进去，8 连接下载
  5 MB 与 60 MB，SHA256 与源文件一致。
- **暂停 → 继续 → 完成**：暂停时状态是 `paused`（不是 `cancelled`），
  进度冻结；继续后重新启动并下完，SHA256 仍然一致。
- **自定义协议**：`idmshadow://dl?url=...&name=...` 注册在 HKCU，
  单实例机制把链接转交给已有实例，任务正常创建并开始下载。
- **鉴权**：没有 token 一律 401，token 也可通过 `?token=` 传。
- **界面**：任务列表、进度条、状态徽章、设置面板（地址/token/限速/目录）都正常。

## 关键设计决定

1. **落盘用预分配单文件 + 偏移写**，不是分片文件再合并。
   断点续传因此几乎免费，多连接之间也不会互相干扰。
2. **已完成字节用 `IntervalSet` 表示**，落进 `intervals` 表。
   它是断点续传的唯一事实来源，也让属性测试可以验证"不重叠、不留洞"。
3. **分段边界是会动的**。`Segmenter` 裁决"谁负责哪一段"，
   worker 只管从自己区间的起点往后读。重平衡定时器每 2 秒调一次：
   淘汰慢连接、把文件尾部按速率切给更快的空闲连接。
4. **worker 与区间解耦**。区间被重分割时，worker 中断当前请求，
   按新区间重新发 Range 请求，不会写出错位的字节。

## 过程中被测试抓出来的真实 bug

记录下来，因为它们都属于"看起来对、实际错"的类型：

- **区间合并 off-by-one**：`[0,1)` 和 `[2,3)` 之间有洞，却被合并成了 `[0,3)`。
  属性测试的"字节记账精确"断言抓到。
- **worker 每 16KB 断一次**：比对区间时用了区间起点，
  而 `complete()` 每写一块就会推进起点，于是每次比对都失败。
- **多连接形同虚设**：第一条连接把 `max_segment_size`（64 MiB）整个领走，
  其它连接没活干。改成按剩余量的四分之一分配。
- **RFC 5987 文件名解析**：`splitn(2, '\'')` 把第二个单引号留在了值里，
  文件名变成 `'中文.txt`。
- **测试服务器少发一个字节**：`Content-Length` 说 N，实际发 N-1，
  reqwest 报 "error decoding response body"，表现为无限重连。

### 换库的理由

原计划的 `bip` crate 编译不了：它要 nightly（`#![feature(alloc)]` 和已被移除的
`std::rt::heap`）。`bip-rs` 那个 `bittorrent` crate 0.2.0 是个空壳。
最后用了 `bittorrent-rs` 0.3.0——stable 能编译，功能更全。

它缺入站 TCP 监听，我们在 `engine/src/bt/listener.rs` 里补上了。
